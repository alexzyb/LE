🔍 二、 核心关键指标详细解释 (Deep Dive into Meanings)
针对你特别提出的疑问，这里用工程师的视角做详细解答：

关于 Totaliser (总计/累计量) vs Production (产量/瞬时速率)
你在数据中看到了大量的 Totaliser 和 Production，这是工业 SCADA 数据中最容易混淆的两个概念，我们用**“汽车仪表盘”**来打比方：


Production (生产率): 就是“迈速表 (Speedometer)”

  * 在 Complete_Plant 中，这是当前的瞬时生产速度，单位是 t/h (吨/小时)。
  * 如果你看到数值是 20，意思是“如果机器保持现在的节奏跑一个小时，能产 20 吨”。这就是你之前用来对比 24 t/h 目标 计算 OEE Performance 的那个数值。

Totaliser (累计量): 就是“总里程表 (Odometer)”

  * 你会发现 Totaliser 的数值巨大，并且永远在增加，不会清零（除非系统重置）。例如 Truck_Loading_Station 中的数值直接达到了 225940 甚至更高。这是因为它是从机器安装第一天起，皮带秤上压过去的所有颗粒的总重量。
  * 你怎么用它？ 计算“当班总产量”。假设早班 06:00 的 Totaliser 是 100,000 吨，下午 18:00 交班时 Totaliser 是 100,250 吨。那么你用 Python 代码写：100250 - 100000 = 250 吨，这就是这一个班次真实产出的总吨数。

关于 Fuel Level 和 Infeed Totaliser (料仓数据)
你可能好奇，为什么叫 "Fuel" (燃料)？


行业背景： Land Energy 生产的就是 木颗粒燃料 (Wood Pellets)，用于生物质发电和供暖。所以在他们的控制系统中，原料或成品经常被统称为 "Fuel"。
Fuel Level (料位): 这是一个状态值，单位通常是 吨 (t) 或者 百分比 (%)。它告诉你“现在仓里还有多少货”。它会随着进料上升，随着出料下降。这对于厂长非常重要，如果仓空了（Starvation），即使制粒机没坏也得停机等待。
Infeed_Totaliser (进料累计): 也是一个“里程表”，记录这辈子一共往这个料仓里灌了多少吨原料。


为什么频率分布是这样的？（非常合理的工程设计）
你提取的频率分布证明了 Baumgartner 的数据采集逻辑是非常成熟的：


1 秒级 (制粒机 电流/速度/温度): 因为制粒机是整条产线的“心脏”，它的工况瞬息万变。堵机 (Blockage) 往往在几秒钟内发生（电流瞬间飙升到 1000A），因此必须用 1 秒的超高频来捕捉异常，这是我们算 OEE Downtime 最完美的精度。
30 秒级 (全厂总产出): 皮带秤 (Belt Weigher) 的瞬时速率不需要 1 秒读一次，因为物料在皮带上是均匀分布的，30 秒读取一次足以平滑掉毛刺，反映真实的 t/h。
1 小时级 (料仓液位和发货装车): 料仓巨大（比如能装几百吨），里面的液位变化非常缓慢。卡车装车也是按小时计的，所以 1 小时采样一次完全足够，既省存储空间又合理。

⚠️ 工程师警告：你的代码必须处理的三个“脏数据”
既然你要做 Dashboard，我必须提醒你，这批 Live Data 里有很多传感器的“脏数据”，如果你直接用公式相除，你的图表会立刻崩溃：
坑 A：出现负数（传感器零点漂移）


证据： 在 2022年4月22日，数据中出现了 -263.75 这种离谱的负数；还有 -13.06 等小负数。
物理真相： 现实中料仓不可能装“-263吨”的货。这通常发生在料仓完全空了（Empty）的时候，由于温度变化或皮重未校准，称重传感器出现了向下的负向漂移（Zero Drift）。
代码解法： 在换算前，必须用 MAX(0, value) 把所有负数强制归零。

坑 B：极其离谱的天文数字（系统错误码）

证据： 在 2022年9月27日，读数突然变成了 406270.5 (四十万吨)！还有极端的负数如 -406642。
物理真相： 这绝对不是实际重量，而是 SCADA 系统或 PLC 在断电、重启、或通讯故障时抛出的错误默认码（Fault Codes）。
代码解法： 设定一个合理的物理上限（比如 IF value > 1200 THEN Return Null），把这些错误值过滤掉，不要让它们把你的折线图 Y 轴撑爆。

坑 C：带有长尾数的小数（精度冗余）

证据： 数据记录为 501.1875, 1017.34375 等。
代码解法： 在 UI 上展示时，没人关心 0.0001 吨的颗粒，直接 Round(value, 0) 取整数，或者转成百分比后保留 1 位小数即可。

💡 总结：你在后台 (Python/Pandas) 应该写的清洗逻辑
把以下逻辑写进你的数据处理脚本，你的 Silo Dashboard 就会非常稳健：
text# 设定从数据中发现的最大物理容量
MAX_CAPACITY = 1017.0 

def calculate_silo_percentage(fuel_level_tons):
    # 1. 过滤掉系统错误的天文数字
    if fuel_level_tons > 1500 or fuel_level_tons < -1000:
        return None  # 标记为数据异常或离线
        
    # 2. 处理负数漂移，将负数视为 0 吨
    actual_tons = max(0, fuel_level_tons)
    
    # 3. 计算百分比，并限制最高为 100% (防溢出)
    percentage = (actual_tons / MAX_CAPACITY) * 100
    percentage = min(100, percentage) 
    
    # 4. 返回保留 1 位小数的结果
    return round(percentage, 1)

Complete Plant Totaliser 到底是什么？
它不是数字的相加，它是真正的“总水表”。 根据录音，这个数据点来源于“3台制粒机后的出料传送带皮带秤（discharge conveyor for the 3 ms）”。所有被压制出来的颗粒，在离开制粒机后，必须首先经过这个皮带秤。 因此，Complete Plant Totaliser 是整个工厂绝对的总产量，不依赖于任何下游料仓的加减运算。

Complete Plant Totaliser 是否等于 Silo 1 + 2 + 3？
结论：不等于。不能用 Complete Plant = Silo 1 + 2 + 3 这种简单的等式。
正如我们之前在业务逻辑中探讨的，Complete Plant Totaliser 是安装在制粒机总出口的“总水表”，代表工厂绝对的总生产量。
绝大部分颗粒确实会流入 Silo 1、2、3（这就是为什么它们的 Infeed Totaliser 会不断增加）。但在实际生产中：
旁路直装 (Bypass)： 颗粒有时会绕过 Silo，直接送入包装线或卡车。
物理损耗： 从制粒机到料仓的皮带传输过程中，会有粉尘抽吸和筛分损耗。
